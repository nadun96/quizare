# Implementation decisions

Choices made where the Business Analysis (BA) document leaves room or poses
an open question. Each entry cites the BA/architecture source it relies on.
Open questions (BA §14, Q-01…Q-10) are answered provisionally here and can be
changed through configuration where noted.

| ID | Decision | Basis |
|----|----------|-------|
| D-01 | Ubuntu deploy target (systemd, Caddy). Code stays cross-platform; development and tests run on Windows. | Architecture §1.4; spreadsheet OS row conflicts with its own memory notes ("Linux OS") |
| D-02 | Students and teachers can log in before verifying their email. Verification is tracked (`email_verified`) and a reset link also verifies. | BO-2 (QR scan → first question < 90 s); FR-ACC-01 requires verification to exist, not to gate login |
| D-03 | Admin approval of teachers is a platform policy toggle, off by default. | FR-ACC-05 (S, "if institution requires"), Q-09 |
| D-04 | Deleting a user anonymises the account (email, name, password scrubbed; sessions revoked) instead of removing rows, so attempts and results survive. | NFR-04 deletion on request; BR-16 preserve results |
| D-05 | Admins are created only with `server create-admin`; there is no HTTP route. | BA §4 roles; least privilege |
| D-06 | Per-IP rate limits are generous (burst 300) because a classroom shares one NAT address; the per-account limit (10 burst, 1 per 30 s) stops guessing. | ADR-13 rate limiting; BO-2 |
| D-07 | Integration tests run against a real PostgreSQL 16 (embedded, or `QP_TEST_DATABASE_URL`). | ADR-03; avoids mock/prod divergence |
| D-08 | Q-06: by default a QR session join auto-enrols the student in the classroom (`auto_enrol_on_join=true`); teachers can turn it off per classroom, which then requires enrolling by classroom code first. | BR-02 ("if the classroom allows it"), BO-2 |
| D-09 | Once a student has entered their classroom student ID, only the teacher can change it. It is attached to every answer, so students must not be able to rewrite it mid-term. | BR-03, FR-CLS-05 |
| D-10 | Settings keys can be set only at the levels BA §7 lists for them, and this is validated on write. The admin's platform layer can set any key. Time extensions and pauses are not settings: they add up rather than override, so they are stored with the session and attempt. | BA §7 table and timing rules |
| D-11 | A classroom that has results can be archived but not deleted (the delete is refused); this is enforced once sessions exist. | BR-16 by analogy |
| D-12 | CSV import is partial: valid rows are imported and invalid rows are reported with row numbers and reasons. A question code that already exists in the quiz is a row error, so re-uploading only the failed rows works (UC-01 4a). | FR-QZ-05, AC-09 |
| D-13 | CSV extensions to the BA §10.3 template: `\|` escapes a literal pipe; DRAG uses `items` (ordering) or `items\|\|zones` with `item=zone` answers, mirroring MATCH; BLANK_TEXT accepts several answers per blank as repeated `1=a\|1=b`. Optional columns: `negative_marks`, `partial_credit`, `word_limit`, `case_sensitive`, `tolerance`. | BA §10.3 is silent on these |
| D-14 | ESSAY defaults to `llm` evaluation (BR-11 falls back to manual when there is no key). LLM marking is allowed only for ESSAY and BLANK_TEXT; answer-key marking is not allowed for ESSAY. | BA §10.1, §10.3 "defaults by type" |
| D-15 | Resource links are checked off the request path by a River job, with SSRF safeguards (public IPs only after DNS resolution, 5 MB limit, image content type, timeouts, no cookies). Broken links make Ready require `accept_warnings`. | FR-QZ-11, UC-01 6a, ADR-10 |
| D-16 | Live sessions will snapshot questions and keys at session start, so editing a quiz never changes a running session or past results. | ADR-14 |
| D-17 | Q-04: navigation is one-way by default (BR-09). If a quiz allows going back, per-question time limits are ignored, because a per-question timer cannot work when students can return to a question; the quiz limit still applies. | BR-09, Q-04 |
| D-18 | A live session ends by itself once every attempt is finished and the session has been quiet for 2 minutes. The pause leaves time to reinstate a last-minute invalidation before the session closes. | UC-02 step 6, FR-SS-12 |
| D-19 | The 1 Hz ticker reads due deadlines from an indexed Postgres query instead of an in-memory min-heap. The work is the same for 100–300 attempts, and nothing has to be rehydrated after a restart. Deadlines are still timestamps, and paused time is stored as remaining milliseconds. | ADR-07 intent (one shared ticker, restart-safe), ADR-05 |
| D-20 | Q-02: with no quiz limit, an attempt ends when the student finishes the last question or the teacher ends the session. Violations count only while an attempt is running, not during the countdown or a teacher pause. | BA §7 timing rules, BR-07 |
| D-21 | Teacher commands (admit, pause, resume, extend, end, reinstate) go over REST, so they get auth, CSRF checks, auditing and retries. The WebSocket carries server events plus the student's `start`, `violation` and `ping`. | ADR-04 ("WebSocket carries control and events"; answers on REST) |
| D-22 | The `disconnected` violation (heartbeat rule) uses `disconnect_grace_sec` (default 10 s) and follows the violation policy like any other signal. Teachers can reinstate the attempt. | Architecture §1.2 heartbeat rule, R-01/R-05 |
| D-23 | MATCH right-hand items and DRAG items are always shuffled per attempt, because their authored order would reveal the answer. `option_order` controls only SINGLE, MULTI and BLANK_OPT. | BA §7 option order; integrity |
| D-24 | Marking rules. Partial credit is the share of parts that are right; for MULTI it is (right picks − wrong picks) / correct options, floored at 0. Negative marks apply only to an answered question that earns nothing. Unanswered questions score 0 by every method, including essays. An attempt's total is floored at 0. Spelling tolerance is never applied to accepted answers of 3 characters or fewer. | BA §10.1, FR-QZ-09 |
| D-25 | Q-10: release follows `results_release` (default `on_session_end`). Results can be released while LLM or manual marks are still outstanding; the student then sees a "marking in progress" state and AI-marked answers carry a badge. A teacher who wants to review first sets `manual` and releases explicitly; a release can be undone. | BA §7, UC-04 step 5, ADR-15, R-07 |
| D-26 | Result visibility toggles `results_show_answers`, `results_show_correct` and `results_show_feedback` (quiz or session level, default on) were added to the settings, because BA §11 lists them as configurable without naming a level. The rubric is never shown to students. | BA §11 student-facing results |
| D-27 | Invalidated attempts are marked when the session ends, so teachers can still see the answers. They are reported with `invalidated=true`, never count as passed, and are excluded from pass rates. | BR-07, BA §11 invalidation rate |
| D-28 | Q-08: OpenAI, Anthropic and Google Gemini are supported at launch. The Anthropic adapter uses the official Go SDK; the other two use plain HTTP with JSON-schema output. When an Anthropic key is added without a model, it defaults to `claude-opus-5-5`; OpenAI and Google keys must name their model. | Architecture C4 (external LLM APIs), FR-EV-02 |
| D-29 | A teacher's first key becomes their default; `llm_key_id` and `llm_model` settings can pick a different key or model per quiz or question. The API exposes only list (masked to the last 4 characters), add, update label/model/default, test and delete. | BR-10, AC-11, ADR-09 |
| D-30 | LLM jobs use the `llm_marking` queue (4 workers), a 120 s timeout, 4 attempts, and are unique by attempt, question and mode while queued or running. Permanent provider errors (bad key, no quota, bad request, refusal) cancel the job and send the answer to manual marking with a flag. Retryable errors back off; after the last attempt the answer also falls back to manual. A per-teacher rate limit snoozes jobs instead of failing them. | ADR-06, UC-04 exception, NFR-16, R6 |
| D-31 | Results are flagged for teacher review when the score had to be clamped, the answer contains text that looks like instructions to the marker, a very short answer scores above half marks, or the model reports confidence below 0.5. Personal data (emails, phone numbers) is scrubbed when the request is built. | ADR-16 prompt injection and data minimisation, R7 |
| D-32 | Analytics are recomputed by a River job on every results change and at session end. The worker debounces by skipping any job created before the last computation. Average time per question is not reported, because the BA timing rules do not record when each question was viewed; the analytics show total time taken per student instead. | ADR-15, BA §11 |
| D-33 | A public link shares chosen views (`individual`, `question_pct`, `pass_rate`; for a session the default is the session's `results_view`). Students are shown as "Student N" unless the teacher picks `student_id`. Individual answers appear only with `show_answers`. Names and emails never appear. Tokens are 128-bit, stored hashed, shown once, revocable, regenerable and optionally expiring, and pages carry `X-Robots-Tag: noindex`. Invalidated attempts are left out of public views. | FR-RS-01/02/04, BR-13, AC-12, ADR-16 |
| D-34 | The admin console shows counts (users, classrooms, quizzes, sessions, attempts, violations, job queues) and the audit log, never quiz content, answers or keys. Any user can download their own data as JSON. Students and teachers can delete their own account (it is anonymised) after re-entering their password. A scheduled retention job that anonymises old attempts is deferred to a later release. | BA §4 admin restrictions, NFR-04, ADR-16 |
| D-35 | The OpenAPI 3.1 spec is hand-written and held in sync with the router by a contract test (both directions, plus `$ref` and operationId checks) instead of being generated from code annotations, which keeps handlers free of comment boilerplate. Swagger UI is embedded in the binary and loads no inline script, so it works under the strict CSP. Docs are served by default; `QP_API_DOCS=0` turns them off for deployments that should not expose the API surface. | ADR-16 CSP; maintainability |
| D-36 | Developer documentation is part of the frontend (`/docs`), written in Markdown in the repository, so it ships and versions with the code. Mermaid loads only on docs pages, keeping the student bundle unchanged. Tests check that every page, link, anchor and diagram is valid and that every backend module, setting key and migration is documented. The docs are public, like the source they describe. | ADR-11 (bundle size); maintainability |
| D-37 | Containers are an alternative to the single-host install (ADR-01 still holds: one app process). The image is distroless and non-root, the binary has its own `healthcheck` subcommand, and the SPA is served by Go. Compose runs PostgreSQL in a separate container with the architecture's tuning, and offers Caddy behind an opt-in `tls` profile. The same files run on Docker and Podman. For containers only, `QP_KEK_GENERATE=1` creates the master key in a volume on first start, because a bind-mounted 0400 file would be unreadable by the non-root user; the key is still never taken from an environment variable. Startup retries the database (`QP_DB_WAIT_SECONDS`), since not every compose implementation honours health conditions. | ADR-01, ADR-09, ADR-12, ADR-16, architecture §1.4 |
| D-38 | Question text and predefined feedback get a rich text editor (Tiptap, WYSIWYG). The BA treats question text as text ([[n]] blanks in CSV, BR-15 pictures as URL resources), so the text is stored as Markdown in the same field instead of HTML: CSV import and LLM prompts keep working, and there is no stored HTML to sanitise. `body.format = "markdown"` marks editor text; without it, text is plain and renders exactly as before, so existing and imported questions never change meaning (for example `5*3*2`). The dialect adds `[[n]]` blanks, `++underline++` and `$math$` (Pandoc rule, so prices stay text). Images are not part of it; pictures remain resources. Rendering escapes HTML, allows only http(s) and mailto links and runs DOMPurify. The editor, the Markdown renderer and KaTeX are loaded only when needed, so a plain-text quiz keeps the student page at its old size. Markdown text may be up to 10,000 characters (plain text stays at 5,000). | FR-QZ-02, BA §10.3, BR-15, ADR-11, ADR-16 |
| D-39 | UI refresh based on UX research (docs: *UX research & design rules*). The UI kit is daisyUI 5 on Tailwind CSS 4: CSS only, so the student page gains no UI-framework JavaScript (NFR-09), and its CSS-variable themes work under the strict CSP. Light and dark themes are checked for WCAG AA in a test (NFR-14); form-field borders meet 3:1. Status always pairs an icon and text with colour. Students and teachers can choose the theme, the text size (100/112/125%) and reduced motion; the choice is stored per device. The quiz screen shows progress, a visible saving state, and a timer that can be collapsed but expands by itself in the last minute; it announces 5 min, 1 min and 30 s left. Answer options are 56 px tiles with letter markers. The teacher dashboard has live counters, progress bars and toasts. Native `confirm()` is replaced by an accessible modal. Transitions are 150–250 ms and switch off for reduced motion. | NFR-09, NFR-13, NFR-14, FR-PR-01, UC-02, UC-03 |
| D-40 | Live polls are a separate module (`poll` schema) rather than a quiz mode: they have no answer keys, marks or proctoring, and must work without a login. The teacher chooses identity (anonymous, identified, or participant's choice), audience (anyone, or one classroom, which requires identification), pacing (self or presenter-led) and what participants see (live, after answering, when revealed, never). Anonymous participants get a random device token (only its hash is stored, the browser keeps it in localStorage per poll); an anonymous poll never records an account, even for a logged-in user. All seven quiz types plus thirteen poll inputs are supported (choice, star rating, slider, Likert, matrix, word cloud, short and long text, code, number, date, time, file, audio and video). File, audio and video answers are stored in PostgreSQL with strict limits (5 MB files, 60 s audio, 30 s video, 200 MB per poll), sniffed for type, and only the owner can download them; BR-15 (URLs only) covers quiz resources, not poll responses. Results are recomputed only for changed questions, twice a second, and pushed to presenters and, as one shared update, to participants; "after answering" is therefore a display rule applied by each browser, while "never" is enforced by the server. Participants never see names. Teachers can hide answers and words. Charts follow the dataviz rules, with Likert palettes validated for colour-blind separation in both themes. | NFR-10, NFR-13, NFR-14, ADR-05, ADR-13, ADR-16, BR-15 |
| D-41 | Version 2 requirements (V2-01…V2-09) were given by the product owner on 2026-10-06 and are kept privately with the BA document. Student categories (V2-03) are labels per classroom, not global: a student is in many classrooms and each teacher organises their own. A student can be in several categories; a category has a name (unique per classroom) and one of the eight categorical palette colours, shown as a dot beside the name so identity never depends on colour. Categories filter the student list, can be assigned in bulk, and later seed groups (V2-06). Assignment only accepts enrolments of the same classroom. | V2-03, NFR-14 |
| D-42 | Scored polls (V2-01, V2-02) extend polls instead of reusing live quiz sessions, because polls already run without a login, presenter-led, with live results; D-40's "no answer keys" now means "keys are optional". The teacher chooses: scoring on or off; correctness only (default) or a speed bonus, which applies only to presenter-led questions with a time limit, where everyone starts together (a right answer earns 50–100% of its points, linearly over the limit); who sees the leaderboard (off, presenter by default, or everyone); when participants see the correct answer (never, right after answering, when the presenter shows it, after closing, by default the last); and whether the leaderboard shows nicknames or, for logged-in participants, real names (never in anonymous polls). Partial credit follows the quiz marking rules (D-24). Scores are stored with each answer and recomputed when a key, points or scoring settings change. Keys never reach a participant before they are revealed: "after answering" keys come only in that participant's own responses, never in the shared live update, and once a key is visible the answer is locked. The shared update carries only the top 10; each participant's own rank comes from their personal view, and leaderboard rows use an opaque per-poll key instead of participant ids. Nicknames are optional, at most 30 characters, and the teacher can rename anyone. | V2-01, V2-02, BR-13, ADR-16 |
| D-43 | Groups in polls (V2-06, V2-07) belong to the poll, not the classroom, so anonymous polls can have groups too; forming them from classroom categories copies the categories' names and colours and needs participants who log in. Formation is manual, random (each new participant joins the smallest group; a teacher action reshuffles), from categories, or chosen by participants when joining (they can switch until they answer). Acceptance is chosen per poll: every member's answer (combined by sum, average, highest or lowest), the group's first answer, the captain's answer, or the best answer. Average and lowest count silent members as 0, so groups can't improve their mark by letting only the strongest answer. In first-answer and captain modes the server refuses other members' answers (first-answer uses a row lock per group); members see the answer given for their group. The earliest member is captain unless the teacher picks another. Group scores are computed from member scores when ranking, not stored, so changing the rules applies at once. Participants see groups' names, colours and sizes, never members. | V2-06, V2-07, NFR-14 |
| D-44 | Teams in live quiz sessions reuse the group rules of D-43 but not the blocking: every student still sits their own timed, proctored attempt (BR-01, BR-05, FR-PR), and acceptance only chooses which marks count: every member's (sum, average, highest, lowest), the team's earliest answer per question (by save time), the captain's, or the best. The rules are settings (`team_mode`, `team_acceptance`, `team_calc`, quiz or session level), so a quiz can carry its default. Team standings are computed from the stored marks on request, so rule changes apply at once and invalidated attempts never count (D-27); they fill in as members finish and say when marking is still pending. Teams are ranked by percentage of their maximum, because a total of every member's marks would otherwise favour bigger teams. Formation matches polls: manual, random, from classroom categories, or chosen on the join page. Students see their team while taking the quiz and their team's place with their released result; the combining rules live in one shared package for polls and sessions. | V2-06, V2-07, BR-01, D-27 |
| D-45 | Public live leaderboards (V2-08) are share links with two new scopes (`live_session`, `live_poll`), so they inherit D-33's protections: 128-bit tokens stored hashed, revocable, renewable, optional expiry, `noindex`. Real names never appear on a public link, whatever a poll's own setting: students show by classroom student ID or "Student N", poll participants by nickname or "Participant N". The page polls a REST endpoint (3 s while running) instead of opening a WebSocket: viewers are anonymous and possibly many, rankings change at human pace, plain HTTP passes every proxy, and the server caches each link's view for 2 s so a full room costs one computation. Sessions rank by percentage of marks (finished, valid attempts only); polls rank by points. A live token opens only the live page and a results token only the results page, so one kind of link never exposes the other's data. | V2-08, BR-13, D-33, ADR-16 |
| D-46 | Questions added to a running poll (V2-05) go through the normal add endpoint, with placement options: after the presented question or after a given question, and, for presenter pacing, presenting it at once. Placement shifts later positions in one transaction, so answers and other questions are untouched, and the change reaches participants on the hub's next flush (500 ms), inside the 2 s target. The presenter screen reuses the full question editor in a dialog rather than a reduced quick form, so every type, answer key and time limit is available live; live quiz sessions are excluded, because their questions are frozen when the session starts (ADR-14, D-16). | V2-05, ADR-14, D-16 |
| D-47 | The whiteboard (V2-09) belongs to polls, which already have anonymous and identified participants, groups and a presenter screen; a live quiz session stays a proctored test without a shared canvas. Marks are stored as vector strokes on a fixed 1600×900 board, not as images: late joiners load the whole board, every screen draws it sharply at its own size, erase and undo work per stroke, and PNG export is drawn in the browser. Strokes are written over REST like answers (D-40: participant sockets stay read-only) and pushed to every open socket immediately rather than on the 500 ms results flush. Pen lines go out in 200 ms pieces joined by a gesture id, so viewers see a line grow and undo removes all of it; with the push this keeps strokes on viewers' screens well inside 1 s. The teacher decides who draws (teacher only by default, everyone, or chosen groups and participants), as the product owner asked; participants may erase and undo only their own marks. The eraser removes whole strokes (no partial erasing), which keeps strokes small and sync simple. Limits: 20 strokes per request, 2,000 points per stroke, 20,000 strokes per board, and a per-participant rate limit. | V2-09, D-40, NFR-10 |
| D-48 | Users can pick any daisyUI built-in theme and their own main colour, as the product owner asked, without giving up WCAG AA (NFR-14). Measured against our checks, 20 of daisyUI's 35 themes fell short somewhere (coloured buttons, badges or alerts), so `scripts/gen-themes.mjs` tunes each theme: semantic colours are darkened or lightened (hue kept) until they read at 4.5:1 as text, on their soft tints and under black or white text, and the tokens daisyUI lacks (secondary text, field borders, the categorical palette) are derived per theme. A test checks every generated theme with the same rules as ours. Each theme is a separate ~2 KB stylesheet loaded only when chosen, because shipping all of them in the main CSS would have added 9 KB (gzip) to every student page (NFR-09). A custom main colour gets the same treatment in the browser against the current theme. Our two themes stay the default. Icon-only controls use one component: the label is the accessible name and a daisyUI tooltip on hover and focus, or visible text when the user turns on "Always show button labels"; native `title` tooltips and `window.prompt` are replaced by daisyUI tooltips and a labelled modal. Preferences stay per device (D-39). | NFR-14, NFR-09, D-39 |
| D-49 | Users can change their password from the account page: the current password is required (and attempts are rate-limited like logins), other sessions are signed out while this one stays, and an email tells the owner, so a stolen session can't silently take over the account. Profile pictures are capped at 512 KB as asked, accept PNG, JPEG, WebP and GIF (never SVG), and are stored in PostgreSQL (like poll files, D-40) after being decoded, cropped to a square and re-encoded as a 256 × 256 JPEG; re-encoding drops all metadata, including EXIF location in phone photos, and anything that isn't pixels. A picture is shown only to people who already see that person's name: the person, admins, and a teacher and the students of their classrooms; other students never see each other's pictures, and anonymous poll participants have none. The image URL carries a version so browsers cache it permanently and refresh it only after a change. | NFR-04, FR-ACC, ADR-13, ADR-16 |
| D-50 | Hosting from a teacher's own PC needs no domain and no code change: `home.env.example` uses a free sslip.io name for the router's public IP (e.g. `203-0-113-5.sslip.io`), so Caddy's existing `tls` profile gets a real Let's Encrypt certificate after ports 80 and 443 are forwarded. A bare IP over plain HTTP was rejected because session cookies are Secure (ADR-13) and normal certificates aren't issued for IP addresses. Behind CGNAT, a Cloudflare quick tunnel is the documented fallback. API docs are off in this example because the app is on the internet. | ADR-12, ADR-13, D-37 |
| D-51 | The load test showed a class behind one router throttled at poll join (30 at once, then one every 2 s), and in compose every student looked like Caddy's container address. Joins now allow 150 at once per network address, then four a second: a lecture hall joins together, while a script filling a poll with fake participants is still slowed (and the 2,000-participant cap stays). The app believes `X-Forwarded-For` from loopback and from addresses in `QP_TRUSTED_PROXIES`; compose gives Caddy a fixed address and trusts only that one, not the whole network, so a container or a host port forward can't claim another address. The client is the rightmost untrusted entry, never the leftmost, which the client controls. | ADR-12, NFR-10, D-37, D-47 |
| D-52 | Testing found the whiteboard eraser leaving parts of lines. A pen line is saved in 200 ms pieces, and the eraser removed only the pieces it touched. It now removes whole gestures, on screen and on the server (per owner). The same review fixed four ways a screen could drift from the server: pieces sent in parallel could arrive out of order, so each browser now sends one request at a time and batches what was drawn meanwhile; undo could run before a line's last pieces were saved, so it now waits for them; an `add` arriving after its `remove` or after a clear brought strokes back, so screens remember removed ids and `clear` carries the highest id it removed; screens didn't reload after reconnecting, so they now do. For load, the server groups board events per poll for 50 ms, merging adds and removes, which cut messages per screen about fivefold and removed the dropped sockets seen at 300 viewers and 60 drawers. Access settings and the stroke count are kept in memory, a batch is one insert, and simultaneous board loads share one read. Browsers draw new strokes on top of the canvas instead of redrawing the board. Redis was considered and not used: the app is one process (ADR-01), so the hub already fans events out in memory, and Redis would add a network hop and a second service to the 4 GB host without fixing any of the bugs found. Strokes must also stay in PostgreSQL, so late joiners and restarts see the board. It would only help with several app servers, and then for pub/sub only. | V2-09, NFR-10, ADR-01, D-47 |
| D-53 | Teachers found the countdown starting the moment students were admitted, which with automatic admission meant the moment they joined. A new setting, `start_mode` (teacher, classroom, quiz or session level), keeps the BA's flow as the default (`countdown`: FR-SS-05, each student counts down from admission) and adds `teacher`: admitted students wait, with no countdown, until the teacher presses **Start**. The countdown then runs as usual and students may still start early (AC-03). A teacher can also press **Start now** in either mode, skipping the rest of any countdown. Starting for everyone records `sessions.started_at`, so students admitted later count down by themselves instead of waiting for a second press. Waiting students are `admitted` without a deadline rather than in a new state, so the ticker, dashboards and restarts (ADR-05) need no new cases. | FR-SS-05, AC-03, BR-05, ADR-05 |
| D-54 | Teachers and participants can show the whiteboard full screen, whether they draw or only watch. The board covers the window at the largest 16:9 size that fits, so coordinates stay on the fixed 1600×900 board (D-47) and drawing lands where the pointer is. The browser's full screen is requested for the whole page, not the board element, because dialogs ("Clear the whole board?") and messages live outside the board and would be hidden behind an element in full screen. iPhones don't allow page full screen, so they get the in-window view. Leaving the board's full screen exits the browser's only if the board entered it, so the presenter's own full screen is left alone. | V2-09, NFR-13, D-47 |
| D-55 | Every list whose data can grow is paginated on the server (PL-FR-01 to PL-FR-03, ADR-25 proposed in the architecture addendum). Endpoints take `page`, `size` (default 25, at most 100), `q`, `sort` and `dir`, keep their own array key and add `total`, `page` and `size`, so existing callers keep working. Sorting is whitelisted per endpoint and always ends with a unique column, so pages never overlap or skip a row. Most lists page in SQL with a count; lists that are bounded by something else and need another module's data to search or sort by name (a classroom's students, a session's results, a poll's participants and answers) are filtered, sorted and cut into a page in Go, because modules don't read each other's tables (architecture §1.1); only the page is sent. Lists that can't grow past a small fixed size (a quiz's or poll's questions, at most 50) and the live dashboards (at most 200 rows, updated live) stay whole. In the browser, one `Paged` helper keeps page, size, search, sort and filters in the address, so back, forward and shared links restore the view, and remembers the page size per device. Two lists were added because the old ones couldn't reach everything: a poll's participants, and every answer to a question for moderation (live results keep only the newest 300 text answers). The admin user list showed only the newest 50 users and "My results" the newest 200 attempts; both now reach all. | PL-FR-01, PL-FR-02, PL-FR-03, TS-NFR-35, architecture §1.1 |
| D-56 | Managers (PO-27 to PO-29) share the admin's work. When assigning, the admin decides between an existing active teacher, who keeps teaching and gets a "Manage" area (`role` stays `teacher`), and a new manager-only account (`role = manager`), which has no teaching pages and is emailed a 72-hour link to set its password. Both have a row in `auth.managers` listing the features they were given: view users, manage users, teacher approval policy, platform settings, usage, audit log. A new manager has none (PL-NFR-07), and "Manage users" brings "View users", because acting on accounts needs the list. Storage, clean-up, recordings, tutoring resources and backups join the list when they are built; backups will be offered with a warning and never by default (PO-28). Every `/api/admin` route checks its feature on each request (PL-NFR-06); a manager without it gets 404 and the attempt is logged. | D-57 | Storage and backups (PO-25, PL-FR-04 to PL-FR-09). Backups from the admin console don't use `pg_dump`: the distroless container has none, and a host's `pg_dump` must match the server's major version. Instead the server reads the whole database in one `REPEATABLE READ, READ ONLY` transaction, a consistent snapshot that takes no locks writers wait on (PL-NFR-01, tested), and writes each table as PostgreSQL's COPY text, gzipped at the fastest level and encrypted with age under the admin's passphrase (scrypt, about 128 MB and half a second to open). The file is written as `.part` and renamed when complete, so no unencrypted or half-written backup is ever on disk (PL-NFR-04). The passphrase is entered per backup, held in memory only while it runs and never stored, which is why the backup runs in the server process rather than as a River job, whose arguments are stored. A backup records the migrations it was made with, the tables and columns, the sequences and a fingerprint of the master key; River's queue and the backup history are left out. `server restore-backup` builds that schema in an empty database, loads every table in one transaction with foreign keys off and puts them back on (which checks every reference), compares row counts and sets the sequences; `server check-backup` reads and counts a backup without a database. The master key is never in a backup (ADR-09). A backup starts only with twice the database's size free (PL-NFR-05) and one at a time; one interrupted by a restart is marked failed and its partial file removed. Console backups past the backup space (10 GB by default) are deleted oldest first, always keeping the newest. Downloads use a link that works once, for the person who asked, for an hour (PL-NFR-03). The nightly job keeps its own rotation; it now writes a status file, and the console lists its files read-only and warns after 2 days without success. Sizes are measured hourly from PostgreSQL's catalogues (plus free disk space on the backup folder's disk) and kept 90 days for the 30-day chart. Clean-ups always preview first, and the preview and the deletion count the same rows; the areas today are old console backups and uploaded files of polls closed before a date, whose answers stay marked "removed". Recordings, retention clean-ups and tutoring areas join when tutoring is built; the recording limit (5 GB) is stored now. Storage, clean-up and backups are three manager features; backups is never given by default and the admin is warned when giving it (PO-28). Dates in a clean-up mean the start of that day in UTC. | PO-25, PO-28, PL-FR-04 to PL-FR-09, PL-NFR-01 to PL-NFR-05, ADR-01, ADR-09, ADR-16 |
